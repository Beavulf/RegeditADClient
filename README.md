# RegeditAD (ClientRegAD)

RegeditAD — внутреннее корпоративное веб‑приложение для ведения реестров по сотрудникам и управления доступами/правами, тесно связанными с Active Directory. Система автоматизирует процессы приёма, перевода, увольнения и стажировок, фиксирует историю кадровых событий, контролирует выдачу прав в различных системах, формирует отчёты и позволяет быстро находить актуальную информацию по каждому сотруднику. Интерфейс работает в режиме реального времени через WebSocket, отображая изменения в базе данных без перезагрузки страницы.

Проект сделан как «рабочая панель» для операционных задач: быстро находить сотрудника, видеть его текущее состояние, фиксировать события (приём/перевод/увольнение/стажировка и т.д.), контролировать выдачу доступов и выгружать отчёты в Excel.

Архитектура и стек
Приложение построено по схеме client–server: фронтенд на React + Vite + MUI (MUI X DataGrid) и backend на Node.js + Express с базой MongoDB (Mongoose) и WebSocket‑шлюзом. Backend использует MongoDB change streams для передачи изменений в реальном времени, JWT‑аутентификацию (httpOnly cookie), интегрируется с корпоративным LDAP/Active Directory и MSSQL для работы с существующей инфраструктурой. На фронтенде реализованы сложные data‑driven интерфейсы: таблицы с фильтрацией, сортировкой, группировкой, блокировкой записей от конкурентного редактирования, экспорт выборок в Excel (ExcelJS), управление правами и отдельная «карточка сотрудника», агрегирующая данные из различных реестров.

## Зачем этот проект работодателю

- **Сложный домен и много модулей**: реестры кадровых событий + права/доки + «программы»/отчёты + админ‑панель.
- **Real‑time**: данные в UI обновляются через WebSocket, есть уведомления о действиях (insert/delete) и обработка серверных событий.
- **Конкурентное редактирование**: блокировка строк в таблицах (`is_locked`) и управление блокировками из интерфейса (разблокировка доступна администратору).
- **Data-heavy UI**: MUI DataGrid (поиск/фильтры/пагинация), групповые операции, кастомная пагинация, оптимизации через мемоизацию.
- **Экспорт данных**: выгрузка в Excel (ExcelJS + FileSaver), в т.ч. отчёты за период.
- **Инструменты качества/перфоманса**: ESLint, подключён `why-did-you-render` для диагностики лишних рендеров.

## Основные возможности (по коду)

- **Авторизация**: вход через backend (`/login`), роль сохраняется в `localStorage` (`admin`/`manager`).
- **Навигация по ролям**: пункты меню фильтруются по роли, админ‑раздел скрыт для не‑admin.
- **Реестры**:
  - Приём на работу
  - Назначение
  - Перевод / Временный перевод
  - Стажировка
  - Изменение фамилии
  - Увольнение
  - Данные из ADTool
- **Права и АД**:
  - «Дока и НАСТД» (контроль просрочек, выгрузки в Excel, просмотр всех данных за период/«за всё время»)
  - Active Directory (в т.ч. сценарии вроде «сброса»)
- **Карточка сотрудника**: агрегирует историю по реестрам/таблицам, вычисляет текущее состояние (уволен / временно переведён / на стажировке / активен), экспортирует выбранные данные в Excel.
- **Заявки на доступ**: пользователь может «запросить доступ», админ выдаёт роль и создаёт пользователя.
- **Feedback**: форма жалоб/предложений с прикреплением изображения и управлением статусом (для admin).
- **Документы/обновления**: просмотр DOC/DOCX/PDF (в т.ч. конвертация docx → html), страница обновлений из статического HTML.

## Технологии

- **Frontend**: React 18, Vite 5 (ESM)
- **UI**: MUI (Material UI), MUI X DataGrid + Date Pickers + Tree View, Toolpad Dashboard Layout
- **Backend** (отдельный проект `regeditad`):
  - Node.js + Express
  - MongoDB + Mongoose (change streams для real‑time обновлений)
  - WebSocket (`ws` + `ws-rate-limit`)
  - JWT‑аутентификация (`jsonwebtoken`, токен в httpOnly cookie)
  - LDAP (`ldapjs`) и MSSQL (`mssql`, `msnodesqlv8`) для интеграции с корпоративной инфраструктурой
  - Логирование (`winston`, `winston-daily-rotate-file`)
- **Данные / интеграции**:
  - WebSocket: `react-use-websocket` (real‑time коллекции)
  - REST: `axios` (вспомогательные эндпоинты: login, feedback, выгрузки и т.д.)
  - GraphQL: `@apollo/client` (получение токена и запросы, напр. поиск пользователя в LDAP)
- **Утилиты**: dayjs/date-fns, lodash
- **Файлы**: ExcelJS + file-saver, mammoth (doc/docx)

## Как фронт и сервер работают вместе

- **Авторизация и роли**
  - Клиент при нажатии «ВОЙТИ» вызывает `POST /login` на backend.
  - Backend ищет пользователя в коллекции `Users` (MongoDB) и, если найден, возвращает роль и устанавливает httpOnly cookie `token` (JWT).
  - Роль (`admin`/`manager`) также сохраняется на клиенте в `localStorage` и используется для фильтрации навигации и доступа к разделам.

- **WebSocket и real‑time**
  - Клиент подключается по WS к `ws://VITE_SERVER_ADDRESS:VITE_SERVER_PORT`.
  - Сервер при подключении:
    - читает JWT из cookie `token`;
    - проверяет срок действия токена и роль;
    - периодически (раз в минуту) перепроверяет токен и при истечении отправляет команду `logout`.
  - Каждое сообщение клиента имеет структуру `{ type, data }`:
    - `type` — команда (`getCollectionMongoose`, `insertInToCollection`, `updateInCollection`, `deleteFromCollection`, `getAllClientsIp`, `quitClientConnect`);
    - `data` — полезная нагрузка (коллекция, фильтры, тело документа и т.д.).
  - Сервер:
    - проверяет право на действие по таблице `accessControl` (привязка к ролям);
    - вызывает соответствующий обработчик в `msgHandler` (`routes/websocket-routes.js`);
    - для операций записи дополнительно транслирует изменения в MongoDB change stream и рассылает события всем подключённым клиентам (`broadcastMessage`).
  - Клиентский `WebSocketContext`:
    - подписан на сообщения сервера, обрабатывает их в web worker;
    - обновляет локальное состояние коллекций и, при необходимости, показывает уведомления (insert/delete/error/quit).

- **REST‑эндпоинты и вспомогательные сценарии**
  - `/adress` — узнать ip/адрес клиента (используется на странице логина).
  - `/access` — создать документ в коллекции `Access` (заявка на доступ); далее админ через UI переводит запись в `Users`.
  - `/feedback`, `/feedbacks`, `/feedbackdel` — создание/чтение/удаление фидбеков, загрузка изображений через `multer`, хранение путей к картинкам в MongoDB.
  - `/allpdoka` и другие SQL/отчётные маршруты (через `sqlRoutes.js`) — используются для отчётов и выгрузок в Excel.

- **Слой данных**
  - Все ключевые сущности (сотрудники, отделы, реестры, права, компании, договоры, отпуска, стажировки, ADTool и т.д.) описаны через Mongoose‑схемы в `mongoose.js`.
  - В схемах используются:
    - ссылки (`ref`) между коллекциями;
    - pre‑хуки для каскадного удаления/обновления связанных записей (например, при удалении сотрудника или компании).
  - Фронт работает не с «сырым» SQL, а с нормализованными документами MongoDB, которые приходят через WS/REST.

```bash

```

## Переменные окружения (Vite)

Все переменные должны начинаться с `VITE_`.

- **`VITE_SERVER_ADDRESS`**: адрес backend (HTTP + WS + static).
- **`VITE_SERVER_PORT`**: порт backend.
- **`VITE_APP_URI_GRAPHQL`**: URL GraphQL endpoint (используется Apollo Client).
- **`VITE_APP_ADMIN_LOGIN` / `VITE_APP_ADMIN_PASSWORD`**: сервисные креды для получения access token в GraphQL (токен сохраняется в `localStorage` как `authRegeditADToken`).
- **`VITE_DATE_UPDATE`**: версия/дата обновления UI (используется для бейджа `NEW` в разделе обновлений).
- **`VITE_SPRAV_MRT`**: дополнительная ссылка/путь к справочнику (зависит от окружения).

## Контракт с backend (что ожидает фронт)

Проект — **клиентская часть**. Для полноценной работы нужен сервер, который предоставляет:

- **WebSocket**: загрузка/обновление «коллекций» (по именам вроде `Users`, `Sotrudnik`, `Pdoka`, `Priem`, …) и события insert/delete/ошибки/quit; используется семантика команд типа `getCollectionMongoose`.
- **REST эндпоинты** (используются в UI):  
  - `GET /adress` (получить адрес/идентификатор клиента)
  - `POST /login` (получить роль по адресу)
  - `POST /access` (создать заявку на доступ)
  - `GET /feedbacks`, `POST /feedback`, `POST /feedbackdel`
  - `GET /allpdoka` (выгрузка данных для отчётов/экспорта)
  - `GET /static/...` (обновления/документы/курсоры и др.)
- **GraphQL**:
  - `mutation auth(LoginInput) -> accessToken`
  - `query searchUser(...)` (поиск пользователя в LDAP)
